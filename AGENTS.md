# AGENTS.md

How to change Teamtrail safely. For coding agents (Codex reads this file; Claude Code reads it through `CLAUDE.md`) and for people. Read it before you start. Code standards live in `CONTRIBUTING.md`; this file links to them rather than repeating them.

**Keep this current.** A PR that changes the architecture, a data location or one of the recipes below updates this file in the same PR. `packages/core/test/agents-md.test.ts` fails if a path written here doesn't exist.

## What Teamtrail is

Teamtrail is a local trail map for big work done by AI coding agents. A human describes a trail. Agents chart it as a map of decision tickets (`research`, `prototype`, `junction`, `task`, `execute`, plus `review`) with blocking edges, claim tickets over MCP, ask the human questions, and record decisions with evidence. The human steers in the Lookout, a web app served by the `teamtrail` CLI on their machine. Scout is the voice of Teamtrail wherever the human meets it, in the coding agent, the Lookout, Slack, the site and the docs: briefings, framing questions and system lines.

## Product rules

Every change follows these. If a task seems to need breaking one, stop and ask.

- **Agent-agnostic.** Everything goes through MCP tools. Nothing may depend on one model or vendor, and Teamtrail never calls a model itself. Agents write briefs, knowledge and criteria; Teamtrail gives them structure and enforces gates in code.
- **Local-first.** State is plain files in the repo's `.teamtrail/` folder, or in the user's GitHub or Linear tracker. The local product never needs a Teamtrail server. The paid hosted mode is optional, and nothing local may depend on it.
- **Deterministic core.** Lifecycle, state, gates, ranking and selection are code, not prompts. The same inputs always give the same result, and every automated choice carries a human-readable reason.
- **Evidence over claims, and human leverage.** Teamtrail never answers a question or approves anything on the human's behalf. Agents may decide low-risk matters themselves when allowed, and must record those decisions where the human can review them.
- **Not an executor (locally).** The local product doesn't start, schedule or run agents. It may prepare workspaces (git worktrees) for agents that ask.
- **Not a feed of agent activity.** If a feature only makes the activity feed prettier, it doesn't belong here.

### Tracker data (`.teamtrail/` in the user's repo)

- `<trail>/map.md`: trail frontmatter plus the map body (Destination, Notes, Assumptions, Decisions so far, Not yet specified, Out of scope). Assumptions are `S-<n>` lines with their status (holding, challenged, invalidated, confirmed), linked tickets and challenge in an HTML comment marker (`packages/core/src/model/assumptionLine.ts`); accepting a brief adds its assumptions. The format is shared by every adapter (`packages/core/src/model/mapBody.ts`). The frontmatter also holds the trail's verification level and model matching (`model-matching: on`, `model-tiers: [research=fast, …]`; `packages/core/src/adapters/markdown/modelMatchingFront.ts`); GitHub and Linear keep both in the trail issue's meta marker.
- `<trail>/tickets/<n>.md`: ticket frontmatter, body and comments. `<trail>/decisions/<D-n>.md`: decision records.
- `verification.json`: the checks agents' completions run. Committed. Checks get an allowlisted environment (`packages/core/src/lib/childEnv.ts`): variables a project's checks need beyond it are named in `$TEAMTRAIL_CHECK_ENV` on the machine that runs them, never in the repo. The allowlist is not a sandbox: checks run as the user and can still read `~/.aws`, `~/.npmrc`, `~/.ssh`, `~/.kube`, `~/.docker`, the GitHub CLI's `hosts.yml` and Teamtrail's `credentials.json`, and reach the SSH agent socket. That is why a changed check command needs the human's approval, and why that approval covers the argv, not what the command runs. Its commands run only while the file is the one the trail lead approved on this machine (`packages/core/src/verification/checksApproval.ts`); until then completions wait (`waiting-approval`).
- `briefs/<mapId>.md`: the trail's discovery brief and its status. A trail with a brief requires discovery: implementation tickets can't be claimed until the trail lead accepts it. Committed.
- `criteria/<mapId>.md`: acceptance criteria per ticket (`AC-<n>`, kind, optional knowledge source) and the trail lead's confirmation. Required for implementation tickets on trails with a brief; each needs evidence when the work is completed (only `check:` evidence is verified; the rest is shown as claimed). Only the assignee, or the charting agent before a claim, writes them; once confirmed, an agent's change waits, local only, in `.agents/criteria-proposals/<mapId>.json` (`packages/core/src/criteria/criteriaProposals.ts`) until the trail lead takes it; confirming and taking carry the hash of what the Lookout showed (`checkShown` in `packages/core/src/server/shownHash.ts`), as do accepting a brief and every call on a knowledge entry: the request field `hash` is `sha256:` of exactly the text this machine records as approved (`contentHash` in `packages/core/src/trust/trustLedger.ts`): the ticket's criteria as `criteriaContent` writes them (`/criteria/confirm`, and the proposed ones for `/criteria-proposals/accept`), the brief file's text (`/briefs/accept`), the entry as `knowledgeContent` writes it (`/knowledge/call`, served as `hashes` by id); `/assumptions/confirm` sends the assumption's `text` instead. A mismatch is a 409. Committed.
- `knowledge/K-<n>.md`: project and product knowledge entries (suggested, confirmed, assumption, outdated). Committed, so teammates share it.
- `policy.json`: the risk policy, what always needs the human: a level (low, medium, high) per category and path rules (`packages/core/src/policy/`). Agents can't record high-risk decisions themselves. Declared paths are made repo-relative first (`packages/core/src/policy/repoPath.ts`), and judged with the files git saw change. Optional (defaults apply); committed.
- `models.json`: the project's extra models for model matching, model id or glob to tier (`fast`, `balanced`, `strongest`), read before the built-in families (`packages/core/src/model/modelTier.ts`). Optional; committed.
- `workspaces.json`: whether each claimed ticket gets its own git worktree and branch (`teamtrail/<trail>/<n>`, in `<repo parent>/<repo>.teamtrail/<trail>-<n>`). Off when missing; committed. Teamtrail prepares worktrees only: it never merges, pushes or deletes them.
- `attention.json`: the team's attention policy (kind weights, the interrupt threshold, the digest cadence). Optional; committed. Each person's focus hours, focus switched on or ended by hand, and notification channel live in `attention.json` in their user config dir, never in the repo.
- `.attention/state.json`: snoozes and dismissals of attention items. Local only, git-ignored.
- `guides/<id>.md`: installed and hand-written guides (frontmatter plus instructions; `packages/core/src/model/guide.ts`). `teamtrail guides new <id>` writes one from a template; agents can use it once the trail lead approves it (Settings → Guides → Write your own), shown whole and approved by the hash of what was shown. A file with a built-in guide's id overrides it once approved on this machine; until then the built-in stays active. Committed.
- `guides.lock.json`: the version, sha256, source and approved check commands of every guide the trail lead approved. A file that no longer matches is disabled. Committed.
- `guides.json`: guide catalogs to search, in order, before the official one; `"official": false` leaves the official one out, and listing its URL places it yourself (`packages/core/src/guides/guidesConfig.ts`). Read only as approved on this machine (`packages/core/src/guides/catalogsApproval.ts`, a `catalogs` item in Settings → Approvals); the name `teamtrail` is reserved for the official catalog. `guides add <id>` searches them all and refuses an id found in more than one until it's named `catalog/id`. Optional; committed.
- `.events/<mapId>.jsonl`: the append-only lifecycle journal (`packages/core/src/history/journalFile.ts`): transitions, reroute steps and guide changes (project-wide ones in `.events/_guides.jsonl`, Slack owner changes in `.events/_slack.jsonl`), and remote agents' tokens created and revoked (`.events/_remote-agents.jsonl`). Local only, git-ignored.
- `.agents/charted/<mapId>.json`: which agent (trail name and origin) charted each ticket, so it may write the ticket's criteria before anyone claims it, after reconnecting too. Local only.
- `.agents/workspaces/<map>--<ticket>.json` and `.agents/integration.json`: the worktree prepared for each claim (checks and git evidence for that ticket run in it only when it is one Teamtrail prepared, recorded in the machine store; an agent can write this file), and the latest check of active claim branches that changed the same files. The files an agent said it would change (`touches`) live on its lease. Local only.
- `.reroutes/<mapId>/R-<n>.json`: reroute proposals (typed changes, status, what was applied). A pending one freezes the tickets it touches, unless it touches most of the open ones (`wide`); one pending per agent or token, three per trail, a cool-down after a rejection (`packages/core/src/planning/reroute/rerouteLimits.ts`); only the trail lead approves or rejects. An agent ruling a ticket out always makes one, in its own `rule-out` lane (`packages/cli/src/mcp/trail/ruleOut.ts`). Local only, git-ignored.
- `.agents/delivery.json`: messages a connector (Slack) could not deliver, until one gets through (`packages/core/src/delivery/deliveryStore.ts`); repeated failures become a `delivery` item in the attention queue. Local only.
- `.evidence/`: verification attempts, check output and git evidence per ticket, and the latest checklist answers (`checklist.json`).
- `.agents/remote-tokens.json`: the tokens of remote agents (Settings → Remote agents): id, name and the SHA-256 of each token, never the token (`packages/core/src/remoteAgents/remoteTokenStore.ts`). Written only by the trail lead's create and revoke; `remote-tokens-used.json` next to it holds when each was last used, and `mcp-endpoints/<pid>.json` the MCP endpoints being served now, each signed with the machine key by the process that serves it (`packages/core/src/machine/announcementSig.ts`); an unsigned or forged one is ignored. Local only, git-ignored, never in a tracker.
- `.agents/`: cross-process coordination between MCP processes and the Lookout, including sessions, answers (each signed with the machine key; `packages/core/src/agents/agentAnswerSignature.ts`), leases, trail names and the server lock. It no longer holds approvals: those are in the machine store (below); an old `.agents/guides-approved.json` is never read as one. Every writer of a local-only folder goes through `ensureLocalDir` (`packages/core/src/lib/ensureLocalDir.ts`), which git-ignores it on first use.

### Projects registry (the user config dir, never a repo)

- `<config dir>/credentials.json` (mode 0600): tracker tokens and keys, per person: a pasted GitHub token, the token from Sign in with GitHub (`githubSignIn`), the Linear key and Slack tokens (`packages/core/src/server/trackerConfig.ts`). GitHub tokens resolve in this order: pasted in Settings, `$GITHUB_TOKEN`, `$GH_TOKEN`, signed in with GitHub, then `gh auth token`; signing in drops a pasted token.

- `<config dir>/projects/<project id>/` (0700, files 0600; `packages/core/src/machine/machineStore.ts`): what this machine trusts about one repo, where no agent in the repo and no teammate's push can write. `approvals.json` is the trust ledger (`packages/core/src/trust/trustLedger.ts`): the exact content (and its hash) the trail lead approved here for the check commands, accepted briefs, confirmed criteria and knowledge, the risk policy, each trail's and ticket's verification level, and approved reroutes; it is written under a file lock (`packages/core/src/machine/withFileLock.ts`). A file that claims an approval the ledger doesn't hold opens no gate, and a level lowered below the approved one waits (`packages/core/src/verification/approvedLevel.ts`). `pendingTrust.ts` lists what waits; Settings → Project → Approvals, `teamtrail approve` (`packages/cli/src/approve/`) and the `trust` attention item ask. An approval records the content the page showed, never the file read again (`recordShown.ts`); single-item routes require the hash of what was shown (`packages/core/src/server/shownHash.ts`); approving several at once is for the first run on this machine only (`firstRun.ts`) and adopts only content committed to git as it is (`withCommitted.ts`), journaled under `_trust`. The first run lasts until the human's first approval, and anything committed before then is offered in that first bulk adoption; an item with no file (a level or type on GitHub or Linear) comes along only when it lowers nothing (`adoptableWithoutFile.ts`). A ticket's type is recorded when its trail's level is set or it is claimed, and the trail level applies by that type; a trail level never recorded here is held at the approved config's default until adopted. `guides-approved.json` is the guide lock as approved here, `tracker-approved.json` the tracker this machine uses (`packages/core/src/server/trackerPin.ts`: a `trackers.json` naming another waits for the human), `outbox/` the tracker writes queued while offline (queues and accepted-settings records are keyed by the target plus a hash of it, `outboxKey`; files under the old key move on first use) (writes an older version queued in the repo's `.outbox/` are only shown, then sent or discarded by the trail lead: `packages/core/src/adapters/remote/legacyOutbox.ts`), and `worktrees.json` the worktrees Teamtrail prepared, the only folders checks run in or removal touches (`packages/core/src/workspaces/trustedWorkspace.ts`). The id is the full sha256 of the folder's real path as the file system spells it (`packages/core/src/machine/machineId.ts`), so a repo that moved is asked again.
- `<config dir>/machine.key` (0600): this machine's secret, which signs answers to agents' questions (`packages/core/src/machine/machineKey.ts`). When the config dir can't be read (an agent's sandbox often blocks it), nothing that needs it goes through and both the agent and the human are told why (`packages/core/src/machine/machineAccess.ts`). Limits: all of this stops an agent that can only write files in the repo, and a teammate's push. An agent that can read files in the user's home can read `machine.key`, and any local agent can call `answer_question`. An agent whose sandbox can write the config dir can approve for itself (`teamtrail approve --hash`, or by writing `approvals.json`); where the sandbox blocks the config dir, Teamtrail fails closed. Approving check commands covers their argv, not what they run (`npm run check` runs `package.json` scripts an agent can edit).

- `<config dir>/projects.json` (`$TEAMTRAIL_CONFIG_DIR`, else XDG, else `~/.config/teamtrail`): the repos one Lookout supervises, each with a short id hashed from its tracker folder's real path (`packages/core/src/projects/`, types in `packages/core/src/model/project.ts`). `teamtrail projects add|list|remove` edits it; `teamtrail mcp` and `connect` add their repo on start unless `--no-register`, `$TEAMTRAIL_NO_REGISTER` or the registry's `autoRegister: false`. Nothing new is written inside a repo; a project another live `teamtrail` serves (its `.agents/server.json`) is only read here, and its URL is offered as a link only when the lock carries this machine's signature (`packages/core/src/projects/elsewhereUrl.ts`).

GitHub Issues and Linear store the map and tickets in the tracker instead (`packages/core/src/adapters/remote/`), with the same body format. The local folders above are still used for the journal, evidence and agents.

Tracker content is trusted by who wrote it (`packages/core/src/adapters/remote/writer.ts`). Anything the token's own account writes is trusted as this machine's (the `viewer` in each trail query), so local agents using `gh` as the same login act as you, as they do when they write files in markdown mode. Teammates are GitHub collaborators with write access (asked of GitHub per login, a 404 or read-only answer counts at once, `github/githubPermissions.ts`) or Linear members who aren't guests or deactivated. They can claim, set status and reviewOf, and close tickets. Their author and decision markers count as theirs, never as this machine's trail lead: everyone not this account is shown by tracker identity (`@mona`, `Grace (@grace)`), and their records are kept apart (`teammateDecision.ts`: `postedBy`, ids like `D-9@mona`). Anyone else's markers are inert text. Markers are read only where Teamtrail writes them (`packages/core/src/model/markerText.ts`). An issue's verification level, checks, guide and model matching are taken as-is only when this account wrote them, or this machine accepted them before. A body counts as this account's only if every version in its edit history is. Only the trail lead's own settings actions accept settings: they pass `confirm` (`TicketMetaPatch`/`MapMetaPatch`), and so does Accept as is / Keep stricter on the queue item (`planning/lifecycle/confirmTrackerSettings.ts`, `POST /trackers/settings/confirm`). A claim, a status or an edit never does, even though it rewrites the body. Otherwise the accepted settings stay in force and the change waits in the attention queue. With nothing accepted (a new machine, a lost or edited record), the issue's own settings apply, flagged `settingsUnconfirmed`. Verification and model tiers then take the stricter of them and the project's (`verification/policy.ts`, `planning/matching/tierOfTicket.ts`), and completions wait until the human settles them. The record is in the machine store, `<config dir>/projects/<project id>/tracker-settings/<kind>-<target>.json`, signed with the machine key (a file this machine's Teamtrail didn't write holds nothing), read and written only through `packages/core/src/adapters/remote/acceptedSettingsFile.ts` (rules in `packages/core/src/adapters/remote/settingsInForce.ts`); the old in-repo `.agents/tracker-settings/` is never read.

### Signed state (markdown tracker)

A trail's files are plain repo files, so an agent or a teammate's push can edit them and skip every MCP gate. What gates read, and what says the human decided, counts on this machine only as Teamtrail wrote it here (`packages/core/src/signedState/`):

- **Signed fields** (`stateFields.ts`): a ticket's `type`, `hitl`, `state`, `close_reason`, `assignee`, `status`, `blocked_by`, `review_of`, `verification`, `checks`, `guide`; a trail's `mode`, `destination` (a hash of the section), `verification`, `guides`, `model_matching` and each assumption's status (a deleted assumption line is a change too); a decision's `id`, `ticket`, `decided_by`, `source`, `source_ref`, `supersedes`, `superseded_by`, `risk` and `words` (a hash of the question, the answer, the summary, the rationale, the alternatives, the assumptions it relies on and the human's words in the transcript). Titles, ticket bodies, comments and notes are free text, never signed.
- **The record**: `<config dir>/projects/<project id>/signed-state/<trail id>.json`, one per trail, HMAC-signed with the machine key (`stateRecord.ts`). Each item keeps its fields' values and hash, the hash of the whole file as written (to tell a text edit), who wrote it (`lookout`, `agent <name> via MCP`, `accepted by trail lead`, …) and when; a decision and a trail's map also keep their text (a reworded decision, a rewritten destination and deleted assumption lines read, show and revert from it). Written under the trail's file lock together with the tracker file (`signedWrite.ts`), so the Lookout and every MCP process can write at once. A record that is missing, unparsable or not signed here holds nothing.
- **Writes**: every Teamtrail process writes trails through `nodeMarkdownFs` (`adapters/markdown/nodeMarkdownFs.ts` → `signedFs.ts`), including the Lookout's `PUT /file`. A write carries its `base`, the text the writer read (`MarkdownFs.write(path, text, { base })`; the markdown adapter reads and writes in one operation; the Lookout sends the ETag of what it loaded as `If-Match`, and `PUT /file` answers 409 `stale` on a mismatch, `packages/core/src/server/fileRoute.ts`). It signs only the fields the writer changed from its base; a field that changed since then refuses the write when the writer changed it too (`staleWrite.ts`) and is kept otherwise, and a field it left alone keeps the file's value, so an outside change is never signed by a later write. Files are written through a temp file and `rename`, never through a symbolic link anywhere in the path (`trackerFileWrite.ts`, Revert too); files over 1 MB are never read whole (`oversized`, a change). `rawMarkdownFs.ts` is the folder as it is, for what must see the files themselves.
- **Reads** (`effectiveText.ts`, `judgeItem.ts`): a field that differs from the record falls back to the signed value, and a ticket with any outside change is held (`status: blocked`). Once the project has any signed state on this machine (`projectSigned.ts`: the first signed write or acceptance), a map or ticket nobody signed here was added outside Teamtrail: a trail renamed or copied, a ticket file copied in. Such a ticket is held (blocked, a `junction`, `hitl`) and Teamtrail refuses to write it until accepted; a trail whose record exists but whose `map.md` is gone is removed (one change). Before that (a fresh clone, the upgrade), an unsigned ticket is open, unclaimed and has no status or overrides. An assumption nobody signed is no more than `holding`; a decision is not a decision. A removed ticket or decision still reads from the record. A text-only edit is allowed and marked. Parsing is cached per file text, the record per inode and mtime.
- **The human** (`outsideChanges.ts`, `stateItems.ts`): each outside change is a `state` item in `pendingTrust`, so it shows in Settings → Approvals (old → new per field), the `trust` attention item (blocking) and `teamtrail approve`. Accept signs what the page showed (`acceptState.ts`, through `approveTrust`, hash-bound, journaled); A trail's maps and tickets nobody signed are one item per trail. Revert writes the signed values back (`revertState.ts`, `POST /trust/revert`, this machine only, journaled), or, for files nobody signed, deletes them only when the request names each (`remove`) after the Lookout's own confirm; it is not offered for an added or removed trail, nor for a decision on a trail whose record can't be read. `GET /signed-state` gives the Lookout its marks (ticket inspector and decision detail). Bulk accept is for the state first run only (`stateFirstRun`: ends at the first signed write or acceptance), committed files only, and never an item this machine signed (`standing: changed`).
- **Limits**: a teammate's push shows as changed outside Teamtrail on every other machine until accepted there. An agent that can write the config dir can forge records, as it can approvals; one that can reach the Lookout's port can write through `PUT /file` as the Lookout. Another device on the network may change only a ticket's text, state, status and close through it (`LAN_TICKET_FIELDS` in `packages/core/src/server/trustFields.ts`), never create a trail or ticket. GitHub and Linear trackers use their own authorship rules (above), not this.

### Core modules (`packages/core/src`)

- `model/`: types (`types.ts`: `MapDoc`, `Ticket`, `TicketType`), lifecycle phases and journal entries (`lifecycle.ts`), frontmatter and map body formats, the product name and slug (`brand.ts`). `model/safeText.ts` is how free text never becomes structure: every serialiser that embeds text in something it parses back (frontmatter values, comment and transcript headings, map and brief sections, criteria lines, assumption lines, the `<!-- teamtrail:… -->` markers of the GitHub and Linear formats) passes it through `oneLine`, `guardLines` or `guardMarkers`, and its reader through the counterpart. The guards trim before they guard, since writers and readers trim blocks; ticket files (format 2) also start their comments at a delimiter only Teamtrail writes. New numbered files (tickets, decisions) are created exclusively (`adapters/markdown/createNumbered.ts`), because several processes allocate at once. A new format, or a new field in one, does the same; `packages/core/test/safeText.node.test.ts` round-trips hostile strings through all of them. `model/webUrl.ts` (`webUrl`) is the one check for a URL from data before it becomes a link.
- `adapters/`: the `TrackerAdapter` interface (`adapter.ts`), the markdown adapter (`markdown/`), GitHub and Linear (`remote/`; `remote/github/githubAccount.ts` and `listGitHubRepos.ts` answer who a token is and which repos it can track; `remote/linear/linearViewer.ts`, `listLinearTeams.ts` and `listLinearProjects.ts` answer whose a Linear key is, which teams it can access and a team's projects), and an in-memory adapter for tests.
- `planning/`: graph derivation (`derive.ts`), charting and other operations (`operations/`), lifecycle transitions (`lifecycle/`), decisions (`decisions/`), metrics, delivery across trails (`performance.ts`, `performanceRecommendations.ts`) and the away briefing (`briefing.ts`).
- `verification/` and `evidence/`: checks, review, approvals, outcomes, git evidence and PR/CI sync.
- `agents/`: leases, trail names, agent docs and returning stalled claims to the queue.
- `discovery/`: the discovery brief model, file format, gate (`claimableTypes`, `gateReason`) and store.
- `criteria/`: acceptance criteria, matching them to completion evidence (`checkCriteria`), and the store.
- `knowledge/`: knowledge entries, file format, search, per-ticket selection (`selectKnowledge`), staleness from file hashes, and the store.
- `policy/`: the risk policy: defaults, file parser, store, `riskLevelFor` (the level of a call from its category and paths), `policyViolations` and `decisionsByRisk`.
- `workspaces/`: safe parallel work: the setting and its parser, `prepareWorktree`, touch-set overlaps (`globsOverlap`, `touchOverlaps`), the integration check (`scanIntegrations`, `findIntegrations`) and the trail lead's integration ticket (`addIntegrationTicket`).
- `planning/assumptions/` and `planning/reroute/`: trail assumptions (add, seed from the brief, challenge, confirm, settle) and reroute proposals: `validateReroute`, `rerouteDiff` (the dry run), `frozenTickets`, `applyReroute` (idempotent, resumable), the store and `rerouteTriggers` (signs a reroute may be needed).
- `projects/`: several repos in one Lookout: the registry file and `registerProject`, `projectSummary` (one repo at a glance, from its files only), `mergeAttention` (one queue across repos), `projectBriefing` (the away briefing per repo, via `buildBriefing`), `ProjectBridges` (full bridges started lazily, capped, closed when idle) and `insideRoot` (realpath confinement of file routes).
- `planning/matching/`: model-aware claiming: `tierOfModel` (a session's model to its tier, models.json first), `tierOfTicket` (the one place a ticket's tier is resolved, from the trail's `modelMatching`), `rankForSession` (own tier first, then lower, never higher), `modelWaits` (ready tickets no connected agent's tier reaches), the models.json parser and store. Turned on per trail with `setModelMatching` (trail lead only). Teamtrail never picks or switches a model.
- `guides/`: agent guides. `guideFile.ts` and `guideSchema.ts` parse guide files, `guideLint.ts` (text rules in `injectionRules.ts`, run per line and over the normalised whole text by `textLint.ts`; check argv in `checkArgv.ts`: argv that carries or downloads code is refused, known check shapes are listed in `knownChecks.ts`, and any other program needs the trail lead's acknowledgement, never in bulk) is the schema, size and safety lint, advisory to the human, who still reads every guide, `guideStore.ts` lists built-in (`builtin/`) and installed guides checked against the lock (`guideLock.ts`, `guideStatus.ts`), `resolveGuide.ts` gives a ticket its guide and the checks it adds (add only), `checklist.ts` checks the answers, `installGuide.ts`, `approveCheck.ts` and `removeGuide.ts` are the trail lead's actions, `newGuide.ts` is the template for `guides new`, and `catalogClient.ts` (a GitHub catalog's guide fetched at the commit its index names, sha-checked), `catalogIndex.ts` (Verified only when the index's reviewed hash is the file's), `addFromCatalog.ts` and `findCatalogGuide.ts` (an id across every catalog) read catalogs. `guides update` reads where a guide came from and its approved checks from this machine's record only.
- `remoteAgents/`: who may reach the MCP endpoint over HTTP. `remoteTokens.ts` creates, revokes and verifies tokens (random, stored as SHA-256, compared in constant time), `remoteTokenStore.ts` is the local file, `mcpEndpoints.ts` lists the endpoints being served. The types are in `model/remoteToken.ts`. A completion from a remote agent never runs checks or reads git here (`verification/remoteCompletion.ts`): it goes to the human.
- `signedState/`: the signed state of markdown trails (see Signed state above).
- `attention/`: the attention queue. `buildAttention` ranks everything that needs the human (pure, explainable `reasons`), one source per kind in `attention/sources/` registered in `sources/registry.ts`, scoring, batching, the policy and prefs parsers, and focus: `focusState` (on by hand, quiet hours, paused or off, and until when), `isInterrupting`, and `changeFocus` (focus for a while, end it now, resume quiet hours; `focus.ts`, `changeFocus.ts`). The Lookout shows it in the header (`apps/lookout/src/features/attention/FocusControl.tsx`).
- `activity/`: the activity stream, presence and usage.
- `server/`: the HTTP bridge (`trackerBridge.ts`). Every request to the bridge and the projects hub first passes `requestGuard.ts`: `Host` must be `localhost` or an IP address and an `Origin` must be the server's own, which is what stops DNS rebinding and cross-site requests. The raw file route only touches tracker markdown, never a dot folder or a config file. Routes that change what runs on this machine or whom it trusts (tokens, tracker connection, Slack, risk policy, workspaces, guides, the projects list) answer this machine only, by socket address (`fromThisMachine`); `thisMachineRoutes.ts` is the one list of them (reads that use stored tracker credentials included), and `GET /machine` tells the page which side it is on. Another device on the network can still read, answer and approve; what it reads goes through `redactForLan.ts` (no absolute paths, no tracker account). Tests and end-to-end scripts set `$TEAMTRAIL_NO_GH_CLI` and clear the shell's tokens, so they never use the credentials of whoever runs them. Its route handlers are in `*Routes.ts` (the GitHub repo picker's `GET /trackers/github/repos` is `githubRepoRoutes.ts`, mounted by `trackerRoutes.ts`, with the login and repo lookups cached per token in `githubLookups.ts`; Sign in with GitHub (OAuth device flow) is `POST /trackers/github/sign-in/start|poll|cancel` and `DELETE /trackers/github/sign-in` (sign out) in `githubSignInRoutes.ts`, its state in `githubSignIn.ts`, GitHub's endpoints in `adapters/remote/github/requestDeviceCode.ts` and `pollDeviceToken.ts`, and the OAuth app's client id in `adapters/remote/github/githubClientId.ts` (`$TEAMTRAIL_GITHUB_CLIENT_ID` overrides it, `$TEAMTRAIL_GITHUB_WEB` points it at a fake); the Linear pickers' `GET|POST /trackers/linear/teams` and `/trackers/linear/projects` are `linearTeamRoutes.ts`, with the viewer, team and project lookups cached per key in `linearLookups.ts`), `GET /models` (`modelRoutes.ts`), `/remote-agents` (`remoteAgentRoutes.ts`: the tokens and endpoints, `POST /remote-agents/tokens` and `/remote-agents/tokens/revoke`, journaled, refused cross-site; `watchRemoteAgents.ts` sends the `remote-agents` event), the projects hub in front of it (`projectsHub.ts`: `/projects` routes in `projectRoutes.ts`, `/p/<id>/…` forwarded to that project's bridge, the `projects` event from `watchProjects.ts`), every server's top-level guard (`neverCrash.ts`, `requestUrl` in `http.ts`) and security headers (`securityHeaders.ts`), what another device on the network may not change (`thisMachineRoutes.ts` for routes, `trustFields.ts` with `lanFileRefusal.ts` and `lanCallRefusal.ts` for trust fields whatever the route) and may not read (`redactForLan.ts`, `redactResponse.ts`, JSON and SSE), the `/events` SSE stream and the background loops (`watchLeases.ts`, `watchVerification.ts`, `watchTrackerFolder.ts`, `watchAttention.ts`, `watchIntegration.ts`).

### MCP server (`packages/cli/src/mcp`)

- `server.ts` creates the server; `toolKit.ts` defines how tools are declared (zod schemas, results and errors).
- Tools are grouped in `tools/` (`trailTools.ts`, `ticketTools.ts`, `workTools.ts`, `hitlTools.ts`, `knowledgeTools.ts`, `rerouteTools.ts`, `projectTools.ts` with the read-only `projects_status`, `guideTools.ts`). Their behaviour lives in `trail/` (trail ops, ticket ops, HITL, completion, reviews, leases, sessions, the risk check, the attention summary, assumptions and reroutes, parallel work in `parallel.ts`, model matching in `models.ts`, and guides in `guides.ts`).
- `http/` is MCP over streamable HTTP, built on the SDK's transport and separable from the rest: `createMcpHttp.ts` is a request handler that takes `auth` and `open` and knows nothing about where it's mounted (a hosted workspace mounts the same handler with its own). It checks host and origin (`requestRefusal` in `packages/core/src/server/requestGuard.ts`, shared with the bridge), then the bearer token (`bearerToken.ts`), then the session, which only the token that opened it may use; sessions end on the client's DELETE, a revoked token, an hour without a call (an open notification stream is not a call), or when their token opens more than 8 (`sessionLimits.ts`). Locally, `tokenFileAuth.ts` reads the repo's token file and `remoteAgentOpener.ts` gives every HTTP session its own `TrailAgent`, marked `remote`. `runMcpHttp.ts` is `teamtrail mcp --http` (only `/mcp` on its port); `packages/cli/src/serve/lookoutHandler.ts` mounts the same handler at `/mcp` on the Lookout's port, and the dev server does in `apps/lookout/plugins/trackerFs.ts`: both with `thisMachineOnly`, because that port also serves the bridge, which has no sign-in. Only `mcp --http` is meant to be shared. A token never opens bridge routes. Tools that would assume the agent's files are on this machine check `ctx.remote` (no worktree, no local checks or git evidence, no `projects_status`). A remote agent never speaks for the human: every tool declares `human` in its definition (`none`, `acts` or the `inputs` that claim the human's word), and `packages/cli/src/mcp/remoteGate.ts` is the one place that applies it (tools that act for the human are not registered for remote sessions and a call is refused with the reason; those inputs are refused; a HITL ticket closes only after an answer given in the Lookout or Slack). A new tool that answers, approves or changes a trail lead's setting must declare `acts`; `packages/cli/test/mcp-http.test.ts` pins the list. For every agent, local too, a decision is the human's only by their answer to a question (`trail/humanAnswer.ts`): the answer is tied to the question as asked, its ticket and its risk category, backs one decision, and the record keeps their words; nothing a tool is passed can say who decided. Every string a tool takes is a single line unless declared with `text()`, and every input has a maximum size (`lineSafety.ts`, applied by the tool kit from the tool's own schema); `packages/cli/test/mcp-line-safety.test.ts` walks every tool and pins the free-text fields.
- `instructions.ts` holds the server instructions every agent gets. `packages/cli/commands/scout.md` is the `/scout` command for Claude Code (and the Codex prompt).

### Lookout (`apps/lookout/src`)

- `App.tsx` lays out the zones. `app/` wires the header, map zone, laptop and phone layouts, and dialogs.
- `features/<feature>/` holds one folder per zone or dialog (inbox, map, inspector, activity, plan, decisions, briefing, settings, verification, …).
- Live updates: hooks that refetch when a tracker file changes subscribe through `lib/trackerChanges.ts` (one shared `/events` stream). Don't open a new `EventSource` per hook: browsers allow six connections per host, and requests queue behind open streams.
- `components/ui/` holds the design-system primitives, `hooks/` app-wide hooks (`useLookout.ts` loads data and subscribes to SSE), `lib/` helpers, and `styles/` the CSS per area (tokens in `styles/design-system.css`).
- Projects: `lib/apiBase.ts` gives the page's API base (`?project=<id>` → `/__teamtrail/p/<id>`, home keeps the un-prefixed API; switching projects reloads the page). `?item=<attention item id>` opens a queue item the way its inbox row would (`app/useItemLink.ts`); All projects links to items in other projects with it. `features/projects/` holds All projects, the header's project switcher, the phone home tab's list and the hooks; Settings → Projects is `features/settings/ProjectsSection.tsx`. With one project nothing of it shows.
- Settings → Remote agents is `features/remote-agents/` (`RemoteAgentsSection.tsx`, data from `useRemoteAgents.ts`): the endpoints, one row per token, and the new token shown once with its connect command.
- Settings is a full page that covers the zones, like the Logbook (`features/settings/SettingsPage.tsx`): a side nav of groups (`features/settings/settingsGroups.ts`) and one group at a time, each rendered by its group component (`TrailGroup.tsx`, `ProjectGroup.tsx`, …) from the unchanged section components. `?settings=<group or section>` opens it there (`?settings=guides`, `?settings=slack`); `app/useSettingsPage.ts` keeps the URL in step so the browser's Back returns to the Lookout. On a phone the nav is a list that drills into one group.
- The in-app changelog is `features/settings/releases.ts`.

## Conventions

Follow `CONTRIBUTING.md`: one export per file, 200 lines max, the layout rules, inline type imports, naming, where tests and fixtures go, its **Readable code** rules (no nested ternaries, early returns, flat nesting, object parameters, small functions, explicit variants), and its **Presenting data** rules for the UI (three levels, four type roles, red only for "needs you now", say it once, lists built from `Row` and `MetaLine`). Lint enforces the mechanical ones; write the rest in the same spirit. Run `npm run format` on files you touch.

## Recipes

**Add an MCP tool.**
1. Declare it in the right `packages/cli/src/mcp/tools/*Tools.ts` with a zod schema, title and description; mark read-only tools `readOnly`. State `human`: `'none'`, or `acts` / `inputs` when it speaks for the human, which keeps it from remote agents. String inputs are single-line by default; declare free text with `text()` and make sure the serialiser that stores it guards it (`model/safeText.ts`).
2. Put the behaviour in `packages/cli/src/mcp/trail/`, with core logic in `packages/core` when it's more than glue.
3. Describe when to use it in `packages/cli/src/mcp/instructions.ts` and `packages/cli/commands/scout.md`.
4. Cover it in `packages/cli/test/` (`mcp*.test.ts`) and drive it end to end in `scripts/verify-mcp.mjs`.

**Add a bridge route and SSE event.**
1. Add a `handleX(req, res, ctx)` in `packages/core/src/server/<name>Routes.ts` that takes the shared `RouteContext` (`routeContext.ts`) and returns `true` when it handled the request, following `leaseRoutes.ts`.
2. Mount it in `trackerBridge.ts` next to the others.
3. Push changes with `send('event: x\ndata: …\n\n')` from a route or a loop (see `watchLeases.ts`), and subscribe in `apps/lookout/src/hooks/useLookout.ts`.
4. Trail lead-only actions are journaled. A route that changes what runs on the machine or whom it trusts goes in `packages/core/src/server/thisMachineRoutes.ts`.

**Add a journal entry kind.** Extend the entry types in `packages/core/src/model/lifecycle.ts` and keep the reader in `journalFile.ts` tolerant of unknown kinds. Old journals must still load. Add a test with a mixed old and new journal.

**Add a lookout zone, view or setting.**
1. Create `apps/lookout/src/features/<name>/` with an `index.ts` barrel, and styles in `styles/`.
2. Settings sections go in `features/settings/` (see `SettingsSection.tsx`): add the section to its group in `settingsGroups.ts`, render it in that group's component inside a `SettingsSlot` (which notes whether it's committed to the repo or only on this machine), and it gets its own `?settings=<section>` link. Full views opened from the header follow `features/decisions/`.
3. Check the wide, laptop and phone layouts (`app/LaptopSide.tsx`, `app/PhoneView.tsx`). Zone titles carry an info tip (`components/ui/InfoTip.tsx`).

**Version and release notes.** Every feature PR raises the product version: bump the minor in `packages/cli/package.json` and add a release at the top of `RELEASES` in `apps/lookout/src/features/settings/releases.ts` with that version, the date and 1–4 short, user-facing lines (what changed for the user, not how). A fix PR bumps the patch; add a line only if users would notice. `NEXT` only teases what's coming. `apps/lookout/test/productVersion.test.ts` fails if the two versions differ, and `next` builds publish as `<version>-next.<run>`.

**Extend the end-to-end check.** `scripts/verify-mcp.mjs` drives a real trail through the built CLI and a browser. Add steps for new tools or UI, assert on what the user sees, and avoid timing races: wait on state, not sleeps.

## Checks

- `npm run check` runs everything CI runs: lint, the Prettier check, typecheck, build, the vitest and node:test suites, and `verify:mcp` (needs a build and Chrome; set `CHROME` to its path). It must pass before a PR.
- **Run the app on the dev seed:** `npm run dev` resets the dev project to the seed and starts the Lookout with hot reload. `npm run build -w teamtrail && npm run dev:agent` adds real MCP agents working it. `npm run dev:empty` starts on a brand-new empty tracker folder instead, for the first-run flow. `npm run dev:fresh` is a first-time user from nothing: a new git repo, an empty user config dir and a new browser profile, served by the built CLI (`scripts/dev-fresh.mjs`).
- `main` is protected: one PR per change, merged after CI passes. Releases are covered in `CONTRIBUTING.md`.
