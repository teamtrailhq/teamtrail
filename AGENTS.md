# AGENTS.md

How to change Teamtrail safely. For coding agents (Codex reads this file; Claude Code reads it through `CLAUDE.md`) and for people. Read it before you start. Code standards live in `CONTRIBUTING.md`; this file links to them rather than repeating them.

**Keep this current.** A PR that changes the architecture, a data location or one of the recipes below updates this file in the same PR. `packages/core/test/agents-md.test.ts` fails if a path written here doesn't exist.

## What Teamtrail is

Teamtrail is a local trail map for big work done by AI coding agents. A human describes a trail. Agents chart it as a map of decision tickets (`research`, `prototype`, `junction`, `task`, `execute`, plus `review`) with blocking edges, claim tickets over MCP, ask the human questions, and record decisions with evidence. The human steers in the Lookout, a web app served by the `teamtrail` CLI on their machine. Scout is the voice of Teamtrail wherever the human meets it, in the coding agent, the Lookout, Slack, the site and the docs: briefings, framing questions and system lines.

## Product rules

Every change follows these. If a task seems to need breaking one, stop and ask.

- **Agent-agnostic.** Everything goes through MCP tools. Nothing may depend on one model or vendor, and Teamtrail never calls a model itself. Agents write briefs, knowledge and criteria; Teamtrail gives them structure and enforces gates in code.
- **Local-first.** State is plain files in the repo's `.teamtrail/` folder, or in the user's GitHub or Linear tracker. Everything works without a Teamtrail server except Slack, which is optional and goes through Teamtrail's Scout service (questions, answers and digests pass through it; trails, decisions and approvals never leave the machine). The paid hosted mode is optional, and nothing local may depend on it.
- **Deterministic core.** Lifecycle, state, gates, ranking and selection are code, not prompts. The same inputs always give the same result, and every automated choice carries a human-readable reason.
- **Evidence over claims, and human leverage.** Teamtrail never answers a question or approves anything on the human's behalf. Agents may decide low-risk matters themselves when allowed, and must record those decisions where the human can review them.
- **Not an executor (locally).** The local product doesn't start, schedule or run agents. It may prepare workspaces (git worktrees) for agents that ask.
- **Not a feed of agent activity.** If a feature only makes the activity feed prettier, it doesn't belong here.

### Tracker data (`.teamtrail/` in the user's repo)

- `<trail>/map.md`: trail frontmatter plus the map body (Destination, Notes, Assumptions, Decisions so far, Not yet specified, Out of scope). `<trail>` is the trail's id, named from its title when it is created and never changed after: the first folder name nothing uses yet (`sync`, else `sync-2`, `sync-3`, …; not a trail's folder, archived or removed, nor `briefs` and the other tracker folders, nor a name local-only state is still kept under: a journal, evidence, reroutes, charted record, criteria proposals, leases, workspace records or check runs a hand-deleted trail left behind, which stay as history, `packages/core/src/signedState/trailLocalState.ts`), taken under the trail's lock only while nothing is in it, so two trails never share one (`packages/core/src/adapters/markdown/newTrailFile.ts`, `packages/core/src/signedState/freeTrailFolder.ts`). A trail's `#n` and its tickets' come from one count, handed out once under a lock every Teamtrail process takes (`.agents/numbers.json`, `packages/core/src/adapters/markdown/numberRecord.ts`; the Lookout's page asks for one with `POST /file/number`, this machine only), so trails and tickets created at once never share a number and a removed trail's numbers are never given again; existing ones keep theirs. Assumptions are `S-<n>` lines with their status (holding, challenged, invalidated, confirmed), linked tickets and challenge in an HTML comment marker (`packages/core/src/model/assumptionLine.ts`); accepting a brief adds its assumptions. The format is shared by every adapter (`packages/core/src/model/mapBody.ts`). The destination and notes are markdown documents, their `## ` lines and markers guarded, up to `TRAIL_TEXT_LIMITS` (`packages/core/src/model/trailTextLimits.ts`: 10,000 and 50,000 characters, 100 one-line assumptions), checked by `trailTextProblem` in `chartMap`, `update_trail` and the Lookout's New trail; on GitHub a trail issue whose body would pass 65,536 characters is refused before anything is sent or queued (`packages/core/src/adapters/remote/mapBodyFits.ts`). The frontmatter also holds the trail's verification level, model matching (`model-matching: on`, `model-tiers: [research=fast, …]`; `packages/core/src/adapters/markdown/modelMatchingFront.ts`) and its guides by type (`guides-by-type: [research=architect, task=qa, task=security]`, one `type=guide` pair per entry; missing means the defaults, `[]` means none for any type; `packages/core/src/adapters/markdown/guidesByTypeFront.ts`); GitHub and Linear keep all three in the trail issue's meta marker (`guidesByType`). An older `guides: [...]` (the trail's team from before guides came by type) is still read; see Guides by type below. `archived: true` marks a trail the trail lead archived (`setTrailArchived`, Start over and Archive in the Lookout's trail menu, `apps/lookout/src/features/header/TrailActions.tsx`); GitHub and Linear use the `teamtrail:archived` label, taken from whoever added it, like the plan-only label. An archived trail stays as history and gives no work: it drops out of the active trails (`activeTrails`), Slack and project summaries, `orderNext` offers nothing from it and `claim`/`promoteToTicket` refuse (`assertNotArchived`); agents can still read it by name, and what already waits on the human from it stays in the queue (`packages/core/src/attention/gatherAttention.ts`).
- `<trail>/tickets/<n>.md`: ticket frontmatter, body and comments; `<n>` is the ticket's number from the count above. A ticket's guide overrides are `guides_added` and `guides_removed` (ids); the single `guide` of older tickets still reads, as an added one. GitHub and Linear keep them in the ticket's meta marker (`guidesAdded`, `guidesRemoved`). `<trail>/decisions/<D-n>.md`: decision records.
- `verification.json`: the checks agents' completions run. Committed. Checks get an allowlisted environment (`packages/core/src/lib/childEnv.ts`): variables a project's checks need beyond it are named in `$TEAMTRAIL_CHECK_ENV` on the machine that runs them, never in the repo. The allowlist is not a sandbox: checks run as the user and can still read `~/.aws`, `~/.npmrc`, `~/.ssh`, `~/.kube`, `~/.docker`, the GitHub CLI's `hosts.yml` and Teamtrail's `credentials.json`, and reach the SSH agent socket. That is why a changed check command needs the human's approval, and why that approval covers the argv, not what the command runs. The check guard (`packages/core/src/checkGuard/`) holds a pass whose work changed what its check runs; a check's `guards` names more files it depends on. Its commands run only while the file is the one the trail lead approved on this machine (`packages/core/src/verification/checksApproval.ts`); until then completions wait (`waiting-approval`). The trail lead can also set the checks in the Lookout (Settings → Verification, `apps/lookout/src/features/settings/ChecksEditor.tsx`): `PUT /verification/config` (`packages/core/src/server/verificationConfigRoute.ts`, this machine only) writes the file with exactly those checks, refusing argv that carries or downloads code and asking about unknown programs (`guides/checkArgv.ts`), and approves it in the same step, only over the file as it was loaded (`verification/setChecks.ts`, journaled under `_trust`). Its `gates` say how each verification gate acts, `off`, `observe` (journal what it would hold back, let the work through) or `enforce` (hold it for the human, with a way past in the Lookout) (`packages/core/src/model/gateMode.ts`, read with `packages/core/src/verification/gateModeFor.ts`); a gate that fires journals it with `packages/core/src/verification/recordGate.ts`. The `independent-review` gate compares the model a review ran on with the author's (`packages/core/src/verification/reviewModelGate.ts`): attempts and verdicts keep the model each agent reported (an older attempt's from its session, `packages/core/src/verification/authorModel.ts`), and two ids are the same model when equal once dates, routing prefixes and deployment suffixes are dropped (`packages/core/src/planning/matching/modelIdentity.ts`, `packages/core/src/planning/matching/sameModel.ts`; versions stay distinct, and the vendor is named too). Observe marks the verdict and journals it; enforce holds a same-model PASS (a FAIL stands): the ticket stays verifying, a new review ticket waits for an agent on another model (`packages/core/src/verification/holdForOtherModel.ts`), and the trail lead's approval item names the model (`packages/core/src/verification/approvals.ts`), approving it journaled as any approval and its proof not verified (`packages/core/src/proof/proofGaps.ts`). Agents get reviews of their own model's work last, and under enforce not at all while an agent on another model is connected or once their model's PASS was held (`packages/cli/src/mcp/trail/reviewModels.ts`), told why; the Lookout's Proof section shows the reviewer's model against the author's (`apps/lookout/src/features/proof/reviewModelParts.ts`). The trail lead sets each gate in Settings → This trail → Gates (`?settings=gates`, `apps/lookout/src/features/gates/`), one row per gate with what it held or would have held in the last 14 days (`GET /verification/gates`, every trail's journal, `packages/core/src/verification/readGateLog.ts`; a gate this version doesn't know shows by its raw name): `PUT /verification/gates` (`packages/core/src/server/verificationGatesRoute.ts`, this machine only) writes that one gate and approves the file in the same step, only over the file as it was loaded and only while it is the approved one (`packages/core/src/verification/setGateMode.ts`, journaled under `_trust`). Its `rules` are diff rules (`packages/core/src/model/diffRule.ts`, parsed by `packages/core/src/verification/parseRules.ts`): each an id, `when` globs, a named `check` to run and/or a question to `ask`, and `why` it exists, all shown in the approval diff (`verification/rulesDiff.ts`). Only the approved file's rules apply. A claim with `touches` is told the rules it will likely meet (`verification/rulesForTouches.ts`, `packages/cli/src/mcp/trail/diffRules.ts`); at completion the rules the changed files match (git here, a remote agent's declared paths; `verification/matchRules.ts`) add their checks to the ticket's and keep the agent's `ruleAnswers` on the attempt (`verification/withRules.ts`, `ruleOutcomes.ts`). Under the `diff-rules` gate (`verification/rulesGate.ts`) a completion missing an answer is refused with the list before anything moves, and the ticket shows the held rules (`.evidence/<map>/<ticket>/rules-held.json`, display only) with Go without: the trail lead's waiver for that ticket, in the machine store (`verification/ruleWaivers.ts`, `waiveRule.ts`, journaled as `rule-waiver`). The full ticket's Diff rules lists each rule it went without with Undo (`undoRuleWaiver.ts`, `POST /verification/rules/waive/undo`, the same refusals as the waiver in `assertMayWaiveRule.ts`, journaled as `rule-waiver` with `action: 'undone'`): the rule asks again from the next completion on. The reviewer's ticket and the proof list each matched rule, its check (verified) and the answer (claimed); an unanswered or waived question is a proof gap. Settings → Diff rules (`?settings=rules`, `apps/lookout/src/features/diff-rules/`) lists, adds, edits and removes rules with when each last matched: `PUT /verification/rules` (`packages/core/src/server/verificationRulesRoute.ts`, this machine only) writes and approves them in one step, only over the file as loaded (`verification/setRules.ts`); `?settings=rules&when=<globs>&why=<text>` opens it with a new rule prefilled. The trail lead sets each gate in Settings → This trail → Gates (`?settings=gates`, `apps/lookout/src/features/gates/`), one row per gate with what it held or would have held in the last 14 days (`GET /verification/gates`, every trail's journal, `packages/core/src/verification/readGateLog.ts`; a gate this version doesn't know shows by its raw name): `PUT /verification/gates` (`packages/core/src/server/verificationGatesRoute.ts`, this machine only) writes that one gate and approves the file in the same step, only over the file as it was loaded and only while it is the approved one (`packages/core/src/verification/setGateMode.ts`, journaled under `_trust`).
- `briefs/<mapId>.md`: the trail's discovery brief and its status. Approve the plan (`POST /plan/approve`, `packages/core/src/server/planRoutes.ts` → `discovery/approvePlan.ts`) accepts the submitted brief and confirms every ticket's criteria the page showed in one step, each bound to its shown hash as `/briefs/accept` and `/criteria/confirm` are, all checked before any is approved (409 otherwise), each journaled under `_trust`. Every trail requires discovery, implementation tickets waiting until the trail lead accepts the brief, unless they skipped discovery on this machine (the ledger's `discovery-skipped:<mapId>`; `packages/core/src/discovery/discoveryGate.ts`): a missing or unreadable brief file opens nothing. Committed.
- `criteria/<mapId>.md`: acceptance criteria per ticket (`AC-<n>`, kind, optional knowledge source) and the trail lead's confirmation. Required for implementation tickets on trails with a brief; each needs evidence when the work is completed (only `check:` evidence is verified; the rest is shown as claimed). Only the assignee, or the charting agent before a claim, writes them; once confirmed, an agent's change waits, local only, in `.agents/criteria-proposals/<mapId>.json` (`packages/core/src/criteria/criteriaProposals.ts`) until the trail lead takes it; confirming and taking carry the hash of what the Lookout showed (`checkShown` in `packages/core/src/server/shownHash.ts`), as do accepting a brief and every call on a knowledge entry: the request field `hash` is `sha256:` of exactly the text this machine records as approved (`contentHash` in `packages/core/src/trust/trustLedger.ts`): the ticket's criteria as `criteriaContent` writes them (`/criteria/confirm`, and the proposed ones for `/criteria-proposals/accept`), the brief file's text (`/briefs/accept`), the entry as `knowledgeContent` writes it (`/knowledge/call`, served as `hashes` by id); `/assumptions/confirm` sends the assumption's `text` instead. A mismatch is a 409. Criteria are agreed before the work, so done means verified: an implementation ticket (verification on) nobody claimed whose criteria an agent wrote waits for the trail lead's confirmation before any agent is offered or may claim it, and a pass graded against criteria nobody confirmed waits in verifying instead of closing (`waitsForHuman` in `packages/core/src/verification/outcome.ts`); both are the `criteria` attention item (`packages/core/src/criteria/criteriaHeld.ts`, `packages/cli/src/mcp/trail/criteriaGate.ts`). Confirming checks that pass again by itself, on the same commit, a new attempt graded against the confirmed criteria with the flaky gate and the check guard as on any run (`packages/core/src/verification/checkAgainOnConfirm.ts`, `verifyAgain.ts`; refused when the code moved on or anything but a regrade would be needed, `againRefusal.ts`). A done ticket closed that way by an earlier version goes back to verifying (the `verify-again` event, the trail lead's) and its close replaces its earlier decision. Committed.
- `knowledge/K-<n>.md`: project and product knowledge entries (suggested, confirmed, assumption, outdated). Committed, so teammates share it.
- `policy.json`: the risk policy, what always needs the human: a level (low, medium, high) per category and path rules (`packages/core/src/policy/`). Agents can't record high-risk decisions themselves. Declared paths are made repo-relative first (`packages/core/src/policy/repoPath.ts`), and judged with the files git saw change. Optional (defaults apply); committed.
- `models.json`: the project's extra models for model matching, model id or glob to tier (`fast`, `balanced`, `strongest`), read before the built-in families (`packages/core/src/model/modelTier.ts`). Optional; committed.
- `workspaces.json`: whether each claimed ticket gets its own git worktree and branch (`teamtrail/<trail>/<n>`, in `<repo parent>/<repo>.teamtrail/<trail>-<n>`). Off when missing; committed. Teamtrail prepares worktrees only: it never merges, pushes or deletes them.
- `attention.json`: the team's attention policy (kind weights, the interrupt threshold, the digest cadence, and the review limit `reviewLimit`: how many finished tickets may wait for review before agents start no new implementation work; off when missing). Optional; committed. Settings → Attention sets the review limit (`PUT /attention/review-limit`, this machine only, `packages/core/src/attention/writeReviewLimit.ts`). An agent that can write the file can lift the limit; it paces work, it guards nothing. ### Projects registry (the user config dir, never a repo)

- `<config dir>/credentials.json` (mode 0600): tracker tokens and keys, per person: a pasted GitHub token, the token from Sign in with GitHub (`githubSignIn`), the Linear key and the Slack link to Teamtrail's Scout service (`slack.link`; an own Slack app's tokens from older versions are deleted when Scout is connected or Slack removed) (`packages/core/src/server/trackerConfig.ts`). GitHub tokens resolve in this order: pasted in Settings, `$GITHUB_TOKEN`, `$GH_TOKEN`, signed in with GitHub, then `gh auth token`; signing in drops a pasted token.

- `<config dir>/projects/<project id>/` (0700, files 0600; `packages/core/src/machine/machineStore.ts`): what this machine trusts about one repo, where no agent in the repo and no teammate's push can write. `approvals.json` is the trust ledger (`packages/core/src/trust/trustLedger.ts`): the exact content (and its hash) the trail lead approved here for the check commands, accepted briefs, confirmed criteria and knowledge, the risk policy, each trail's and ticket's verification level, and approved reroutes; it is written under a file lock (`packages/core/src/machine/withFileLock.ts`). A file that claims an approval the ledger doesn't hold opens no gate, and a level lowered below the approved one waits (`packages/core/src/verification/approvedLevel.ts`). `pendingTrust.ts` lists what waits; Settings → Project → Approvals, `teamtrail approve` (`packages/cli/src/approve/`) and the `trust` attention item ask. An approval records the content the page showed, never the file read again (`recordShown.ts`); single-item routes require the hash of what was shown (`packages/core/src/server/shownHash.ts`); approving several at once is for the first run on this machine only (`firstRun.ts`) and adopts only content committed to git as it is (`withCommitted.ts`), journaled under `_trust`. The first run lasts until the human's first approval, and anything committed before then is offered in that first bulk adoption; an item with no file (a level or type on GitHub or Linear) comes along only when it lowers nothing (`adoptableWithoutFile.ts`). A ticket's type is recorded when its trail's level is set or it is claimed, and the trail level applies by that type; a trail level never recorded here is held at the approved config's default until adopted. `guides-approved.json` is the guide lock as approved here, `tracker-approved.json` the tracker this machine uses (`packages/core/src/server/trackerPin.ts`: a `trackers.json` naming another waits for the human), `outbox/` the tracker writes queued while offline (queues and accepted-settings records are keyed by the target plus a hash of it, `outboxKey`; files under the old key move on first use) (writes an older version queued in the repo's `.outbox/` are only shown, then sent or discarded by the trail lead: `packages/core/src/adapters/remote/legacyOutbox.ts`), and `worktrees.json` the worktrees Teamtrail prepared, the only folders checks run in or removal touches (`packages/core/src/workspaces/trustedWorkspace.ts`). `merge-anyway.json` holds the trail lead's Merge anyway records (`packages/core/src/proof/mergeAcceptances.ts`). `lookout-only.json` holds the tickets a high-risk question was asked on (`packages/core/src/policy/lookoutOnlyTickets.ts`, written by `ask_human`, never cleared): `ticketNeedsLookout` reads it next to the session history, so a ticket stays the Lookout's to decide after its question leaves every session doc. Questions about a trail as a whole mark no ticket. `baselines/<mapId>--<ticketId>/baseline-<n>.json` is each claim's git baseline, created exclusively and signed with the machine key (`packages/core/src/evidence/baselineStore.ts`): the commit, branch and dirty files git evidence and the check guard measure a completion from. One that is missing, unsigned or edited is no baseline, and the guard holds such work as `unread`; baselines earlier versions kept in the repo's `.evidence/` are never read. `rule-waivers.json` holds the trail lead's Go without <rule> per ticket (`packages/core/src/verification/ruleWaivers.ts`). `waivers.json` holds the trail lead's Accept without <check> per ticket (`packages/core/src/verification/checkWaivers.ts`; see verification below), so no agent can grant itself one. The id is the full sha256 of the folder's real path as the file system spells it (`packages/core/src/machine/machineId.ts`), so a repo that moved is asked again.
- `<config dir>/projects/<project id>/main-checks.json` (`packages/core/src/mainChecks/mainChoicesStore.ts`): the trail lead's choices about checks failing on main, per trail: Fix main first, the checks dropped for the trail, and Start anyway with the known failures it accepted. Here, not in the repo, since dropping a check or accepting a failure weakens what completions are held to.
- `<config dir>/projects/<project id>/sign-in.json` (`packages/core/src/signIn/signInStore.ts`): the Lookout's paired browsers and waiting pairing codes, for the folder it was started in. Only SHA-256 hashes of the 256-bit session values and of the codes, so reading it signs nobody in; written under a file lock by the Lookout and by `teamtrail pair`, which adds a code there directly for the running Lookout's process, after that server proved it is the one its lock names (no server route mints codes for the CLI). Next to it, `sign-in-<random>.html` (0600, created exclusively; `packages/core/src/signIn/writeSignInRedirect.ts`): the one-time page a browser is opened on, which sends it on to a sign-in link, so the code never goes through argv. It holds an `opened-page` code that works once for one minute (`OPENED_CODE_MS`); a pairing with it is printed in the Lookout's terminal ("Signed in a browser (opened page)", with the time and a short session id; `packages/cli/src/serve/openedPageNotice.ts`, since the browser name is a fakeable User-Agent) and marked with the same short id in Settings → Browsers & devices, and a link refused on this machine tells the human someone else may have used it (`server/signInPublicRoutes.ts`). The Lookout removes each page once its code is used or expires, all of them when it stops, and any a stopped Lookout left when it starts (`sweepSignInRedirects.ts`).
- `<config dir>/machine.key` (0600): this machine's secret, which signs answers to agents' questions and trails' signed records (`packages/core/src/machine/machineKey.ts`; created exclusively, so processes starting together share one). When the config dir can't be read (an agent's sandbox often blocks it), nothing that needs it goes through and both the agent and the human are told why (`packages/core/src/machine/machineAccess.ts`). Limits: all of this stops an agent that can only write files in the repo, and a teammate's push; that includes a claim's baseline, so such an agent can't move the commit its work is measured from to hide a change from the check guard. An agent that can read files in the user's home can read `machine.key`, and any local agent can call `answer_question`. Likewise, while a page `teamtrail` or `teamtrail pair` opened waits (a minute at most), anything that can read the config dir, even without writing it, can read its code and sign in as this machine; the terminal and Settings then show a pairing the human didn't make. `connect claude` offers to turn on Claude Code's sandbox for the project (`packages/cli/src/protect/applySandbox.ts`), so this holds for its shell commands too, not only its own file tools; with the sandbox off, a shell command can still read the config dir. An agent whose sandbox can write the config dir can approve for itself (`teamtrail approve --hash`, or by writing `approvals.json`); where the sandbox blocks the config dir, Teamtrail fails closed. Approving check commands covers their argv, not what they run (`npm run check` runs `package.json` scripts an agent can edit).

- `<config dir>/projects.json` (`$TEAMTRAIL_CONFIG_DIR`, else XDG, else `~/.config/teamtrail`): the repos one Lookout supervises, each with a short id hashed from its tracker folder's real path (`packages/core/src/projects/`, types in `packages/core/src/model/project.ts`). `teamtrail projects add|list|remove` edits it; `teamtrail mcp` and `connect` add their repo on start unless `--no-register`, `$TEAMTRAIL_NO_REGISTER` or the registry's `autoRegister: false`. Nothing new is written inside a repo; a project another live `teamtrail` serves (its `.agents/server.json`) is only read here, and its URL is offered as a link only when the lock carries this machine's signature (`packages/core/src/projects/elsewhereUrl.ts`).

GitHub Issues and Linear store the map and tickets in the tracker instead (`packages/core/src/adapters/remote/`), with the same body format. The local folders above are still used for the journal, evidence and agents.

Each process keeps a cache of the trails it read (`adapters/remote/sync/`) and polls while subscribed. The poll asks what changed from a cursor on, inclusively, leaving out only what it already saw at the cursor (`sync/changeWindow.ts`; GitHub's `since=` window in `github/githubChanges.ts`, free 304s while idle; Linear's `gte` window in `linear/linearChanges.ts`, its first cursor from Linear's newest issue, never this machine's clock); a full page means "read everything again". A changed trail stays pending until a read of it succeeds, one that can't be read never holds up the others, a trail the tracker no longer has leaves the cache and the list, and a read replaces the cached trail whatever changed, its title and archived label patching the trail list (`sync/syncedRefresh.ts`, `sync/syncedStore.ts`). Every five minutes every cached trail and the list are read again, which is what shows a deleted issue or a teammate who lost access. Writes that rewrite an issue body (a claim, a status, an edit, the trail's sections or settings) are laid over the issue as the tracker has it, read just before sending, never over the cache, offline drains too (`sync/syncedSend.ts`); a claim refuses when the tracker names a third assignee, and `claim` reads the tracker itself (`loadMap(id, { fresh: true })`) after a moment to decide who won (`planning/operations/claims.ts`). A queued write the tracker refuses for good stays listed in the status (`SyncStatus.dropped`) and its trail is read again. Adapters are built per tracker, repo or team and token (`server/remoteAdapters.ts`), so a running MCP server follows Settings; open event streams move to the new adapter and send `external.changed` (`server/trackerEvents.ts`). The bridge subscribes to a remote tracker while the Lookout runs and sends a named `tracker` event when a trail changes (`server/watchRemoteTracker.ts`), for views that read through the bridge.

Tracker content is trusted by who wrote it (`packages/core/src/adapters/remote/writer.ts`). Anything the token's own account writes is trusted as this machine's (the `viewer` in each trail query), so local agents using `gh` as the same login act as you, as they do when they write files in markdown mode. Teammates are GitHub collaborators with write access (asked of GitHub per login, a 404 or read-only answer counts at once, `github/githubPermissions.ts`) or Linear members who aren't guests or deactivated. They can claim, set status and reviewOf, and close tickets. Their author and decision markers count as theirs, never as this machine's trail lead: everyone not this account is shown by tracker identity (`@mona`, `Grace (@grace)`), and their records are kept apart (`teammateDecision.ts`: `postedBy`, ids like `D-9@mona`). Anyone else's markers are inert text. Markers are read only where Teamtrail writes them (`packages/core/src/model/markerText.ts`). An issue's verification level, checks, guides (a ticket's overrides, a trail's guides by type) and model matching are taken as-is only when this account wrote them, or this machine accepted them before. A body counts as this account's only if every version in its edit history is. Only the trail lead's own settings actions accept settings: they pass `confirm` (`TicketMetaPatch`/`MapMetaPatch`), and so does Accept as is / Keep stricter on the queue item (`planning/lifecycle/confirmTrackerSettings.ts`, `POST /trackers/settings/confirm`). A claim, a status or an edit never does, even though it rewrites the body. Otherwise the accepted settings stay in force and the change waits in the attention queue. With nothing accepted (a new machine, a lost or edited record), the issue's own settings apply, flagged `settingsUnconfirmed`. Verification and model tiers then take the stricter of them and the project's (`verification/policy.ts`, `planning/matching/tierOfTicket.ts`), and completions wait until the human settles them. The record is in the machine store, `<config dir>/projects/<project id>/tracker-settings/<kind>-<target>.json`, signed with the machine key (a file this machine's Teamtrail didn't write holds nothing), read and written only through `packages/core/src/adapters/remote/acceptedSettingsFile.ts` (rules in `packages/core/src/adapters/remote/settingsInForce.ts`); the old in-repo `.agents/tracker-settings/` is never read.

### Signed state (markdown tracker)

A trail's files are plain repo files, so an agent or a teammate's push can edit them and skip every MCP gate. What gates read, and what says the human decided, counts on this machine only as Teamtrail wrote it here (`packages/core/src/signedState/`):

- **Signed fields** (`stateFields.ts`): a ticket's `type`, `hitl`, `state`, `close_reason`, `assignee`, `status`, `blocked_by`, `review_of`, `verification`, `checks`, `guide`, `guides_added`, `guides_removed`; a trail's `mode`, `destination` (a hash of the section), `verification`, `guides`, `guides_by_type`, `model_matching`, `archived` (null when active, so older records still match; so are `guides_by_type` and a ticket's overrides when unset) and each assumption's status (a deleted assumption line is a change too, and one added outside Teamtrail to a signed trail counts as no more than `holding` until accepted); a decision's `id`, `ticket`, `decided_by`, `source`, `source_ref`, `supersedes`, `superseded_by`, `risk` and `words` (a hash of the question, the answer, the summary, the rationale, the alternatives, the assumptions it relies on and the human's words in the transcript). Titles, ticket bodies, comments and notes are free text, never signed.
- **The record**: `<config dir>/projects/<project id>/signed-state/<trail id>.json`, one per trail, HMAC-signed with the machine key (`stateRecord.ts`). Each item keeps its fields' values and hash, the hash of the whole file as written (to tell a text edit), who wrote it (`lookout`, `agent <name> via MCP`, `accepted by trail lead`, …) and when; a decision and a trail's map also keep their text (a reworded decision, a rewritten destination and deleted assumption lines read, show and revert from it). Written under the trail's file lock together with the tracker file (`signedWrite.ts`), so the Lookout and every MCP process can write at once. A record that is missing, unparsable or not signed here holds nothing.
- **Writes**: every Teamtrail process writes trails through `nodeMarkdownFs` (`adapters/markdown/nodeMarkdownFs.ts` → `signedFs.ts`), including the Lookout's `PUT /file`. A write carries its `base`, the text the writer read (`MarkdownFs.write(path, text, { base })`; the markdown adapter reads and writes in one operation; the Lookout sends the ETag of what it loaded as `If-Match`, and `PUT /file` answers 409 `stale` on a mismatch, `packages/core/src/server/fileRoute.ts`). It signs only the fields the writer changed from its base; a field that changed since then refuses the write when the writer changed it too (`staleWrite.ts`) and is kept otherwise, and a field it left alone keeps the file's value, so an outside change is never signed by a later write; a map's destination rewritten or assumption line deleted outside Teamtrail also stays in the file, still pending (`outsideMapText.ts`), and an assumption added outside it is not signed by the write. Files are created and replaced in the folder's real path, which must be the tracker folder's, and checked again after the write (`trackerFileWrite.ts`). Files are written through a temp file and `rename`, never through a symbolic link anywhere in the path (`trackerFileWrite.ts`, Revert too; `PUT /file` with `If-None-Match: *` creates exclusively, 412 when taken, which the Lookout's numbered creates use); files over 1 MB are never read whole (`oversized`, a change). `rawMarkdownFs.ts` is the folder as it is, for what must see the files themselves.
- **Reads** (`effectiveText.ts`, `judgeItem.ts`): a field that differs from the record falls back to the signed value, and a ticket with any outside change is held (`status: blocked`). Once the project has any signed state on this machine (`projectSigned.ts`: the first signed write or acceptance), a map or ticket nobody signed here was added outside Teamtrail: a trail renamed or copied, a ticket file copied in. Such a ticket is held (blocked, a `junction`, `hitl`) and Teamtrail refuses to write it until accepted; a trail whose record exists but whose `map.md` is gone is removed (one change). Before that (a fresh clone, the upgrade), an unsigned ticket is open, unclaimed and has no status or overrides. An assumption nobody signed is no more than `holding`; a decision is not a decision. A removed ticket or decision still reads from the record. A text-only edit is allowed and marked. Parsing is cached per file text, the record per inode and mtime.
- **The human** (`outsideChanges.ts`, `stateItems.ts`): each outside change is a `state` item in `pendingTrust`, so it shows in Settings → Approvals (old → new per field), the `trust` attention item (blocking) and `teamtrail approve`. Accept signs what the page showed (`acceptState.ts`, through `approveTrust`, hash-bound, journaled); A trail's maps and tickets nobody signed are one item per trail. Revert writes the signed values back (`revertState.ts`, `POST /trust/revert`, this machine only, journaled), or, for files nobody signed, deletes them only when the request names each (`remove`) after the Lookout's own confirm; it is not offered for an added or removed trail, nor for a decision on a trail whose record can't be read. `GET /signed-state` gives the Lookout its marks (ticket inspector and decision detail). Bulk accept is for the state first run only (`stateFirstRun`: ends at the first signed write or acceptance), committed files only, and never an item this machine signed (`standing: changed`).
- **Limits**: a teammate's push shows as changed outside Teamtrail on every other machine until accepted there. An agent that can write the config dir can forge records, as it can approvals; one that can reach the Lookout's port can write through `PUT /file` as the Lookout. Another device on the network may change only a ticket's text, state, status and close through it, never create a trail or ticket; GitHub and Linear calls from there get the same limits (`packages/core/src/server/lanCallRefusal.ts`), both from one definition (`LAN_TICKET_CHANGES` in `packages/core/src/server/trustFields.ts`). Decisions the Decisions view derives from text (a `**Resolution**` or `**HITL transcript**` comment, the map's Decisions so far) are unverified (`packages/core/src/planning/decisions/decisionAudit.ts`, `madeBy` → `unverified`): never the human's call or words, and Decisions so far can't be changed from the network. GitHub and Linear trackers use their own authorship rules (above), not this.

### Core modules (`packages/core/src`)

- `model/`: types (`types.ts`: `MapDoc`, `Ticket`, `TicketType`), lifecycle phases and journal entries (`lifecycle.ts`), frontmatter and map body formats, the product name and slug (`brand.ts`). `model/safeText.ts` is how free text never becomes structure: every serialiser that embeds text in something it parses back (frontmatter values, comment and transcript headings, map and brief sections, criteria lines, assumption lines, the `<!-- teamtrail:… -->` markers of the GitHub and Linear formats) passes it through `oneLine`, `guardLines` or `guardMarkers`, and its reader through the counterpart. The guards trim before they guard, since writers and readers trim blocks; ticket files (format 2) also start their comments at a delimiter only Teamtrail writes. New numbered files (tickets, decisions) are created exclusively (`adapters/markdown/createNumbered.ts`), because several processes allocate at once. A new format, or a new field in one, does the same; `packages/core/test/safeText.node.test.ts` round-trips hostile strings through all of them. `model/webUrl.ts` (`webUrl`) is the one check for a URL from data before it becomes a link.
- `adapters/`: the `TrackerAdapter` interface (`adapter.ts`), the markdown adapter (`markdown/`), GitHub and Linear (`remote/`; `remote/github/githubAccount.ts` and `listGitHubRepos.ts` answer who a token is and which repos it can track; `remote/linear/linearViewer.ts`, `listLinearTeams.ts` and `listLinearProjects.ts` answer whose a Linear key is, which teams it can access and a team's projects), and an in-memory adapter for tests.
- `planning/`: graph derivation (`derive.ts`), the map's layered layout (`layout/layout.ts`; a layer with more than six tickets side by side wraps into a grid, in order of number, while the map is narrower than a wide screen: `layout/wrapLayers.ts`; across the trail each card sits at the median of what it waits on, so a chain runs straight and a review sits beside the ticket it reviews, `layout/placeAcross.ts`; the Lookout joins a wrapped layer of first or last tickets to `main` and the destination with one bracket, `apps/lookout/src/features/map/groupBracket.ts`, and puts them on the line of the one card they join, `apps/lookout/src/features/map/lineAcross.ts`), charting and other operations (`operations/`), lifecycle transitions (`lifecycle/`), decisions (`decisions/`), metrics, delivery across trails (`performance.ts`, `performanceRecommendations.ts`), the away briefing (`briefing.ts`) and whether a trail is done (`trailDone.ts`: every ticket in scope closed as completed and no reroute pending, and, unless the trail lead skipped discovery here (`discoverySkipped`), at least one of them not a discovery ticket, so a trail whose research alone is done isn't done before its plan is charted; `verified` only when every done ticket's proof is, else `unverified`; open pull requests don't hold it back, but a done ticket's work that closed without merging or was reverted does: `trailTogether` says `not-landed` and the trail is `not-done`). MCP tools tell agents the same judgement: `close_ticket`'s `trailDone` and `trail`, and `next_ticket`'s reason, come from `trailDoneFor` (`packages/core/src/proof/trailDoneFor.ts`), with the proofs, the combined run and `discoverySkipped` the Lookout uses.
- `verification/` and `evidence/`: checks, review, approvals, outcomes, git evidence and PR/CI sync. The scope check (`evidence/scopeFlag.ts`): a completion's changed files against the `touches` its agent declared at the claim (taken from the lease before it's dropped and kept on the attempt as `touches`, so re-runs keep it), local and runner evidence alike. - `signIn/`: sign-in to the Lookout. `lookoutSignIn.ts` is one Lookout's sign-in (who a request is, pairing, revoking, event streams held per session), `pairCodes.ts` the single-use codes (a long one for a link `teamtrail` or `teamtrail pair` prints, ten minutes; a short `ABCD-EFGH` one for another device, five minutes), each made for one Lookout process (`instance`, its pid). A session is sent in the `X-Teamtrail-Session` header (`signInHeader.ts`), never a cookie: cookies go to every port of a host. The page keeps it in its own origin's storage. `streamTickets.ts` gives `/events` a single-use ticket, since EventSource sends no headers. `pairAttempts.ts` holds back wrong typed codes per caller (`callerKey.ts`: loopback is one caller, an IPv6 device its /64) and for all other devices together, never a link's 256-bit code, malformed input or loopback for others' guesses. A session belongs to one Lookout start (`start`, with its process): when that Lookout stops, its sessions end, so one a server squatting its port captured opens nothing later. `sessionProof.ts` is how the page checks the server before it sends its session: it got a verifier at pairing (the machine key's HMAC of the session id), sends only the id and a nonce to `POST /session/prove`, and compares HMAC(verifier, nonce ‖ origin), the port taken from the socket, with its own origin. `runningLookout.ts` is what `teamtrail pair` trusts: a live, signed lock whose server proves it is that process (`instanceProof.ts`, a nonce signed with the machine key). A session is `machine` only when a link code is used from this machine; anything else is a `device`. A server that embeds the Lookout can bring its own sign-in instead (`externalSignIn.ts`, the projects hub's `external` access, with `allowedHosts` for its host name and the bridge's `streamKey`): it answers `GET /session` itself and says whether each caller is `machine` or `device`; there is no pairing then. It may name the caller's person (`ExternalCaller.person`, `model/person.ts`): the hub marks the request with them (`server/requestPerson.ts`), as it does this machine's own person from git's `user.name` in the home folder (`server/localPerson.ts`, never a repo's config), and the Lookout's answer routes sign them with the answer (`by`, its own signature `sigBy`, so older answers verify as before); the asking agent's decision then records `decidedByName`, signed as `decided_by_name`, shown in the Logbook and proofs. It names, it never decides: gates still read `decidedBy` and `via`. It may also deny a caller high-risk calls (`highRisk: false`): a caller denied high-risk calls is also another device's, whatever its kind, so it can't change what this machine trusts; the hub marks those requests (`server/limitedRequests.ts`), every Lookout route that records the human's word labels it `lookout-limited` (`server/lookoutVia.ts`), which counts at every gate but the high-risk ones, as a Slack answer does, and such a caller can't close, reopen or record a decision on a high-risk ticket through the file route or a tracker call (`server/limitedFileRefusal.ts`, `server/limitedCallRefusal.ts`), approve a reroute, supersede a high-risk decision (`planning/operations/supersedeGuard.ts`) or change the risk policy.
- `server/`: the HTTP bridge (`trackerBridge.ts`). The projects hub in front of it is the only way in, and every API request needs a paired browser's session (`signInGate.ts`) except `GET /session`, `POST /session/prove` and `POST /pair` (`signInPublicRoutes.ts`; `POST /pair` needs the page's Origin; `project` only to this machine or a paired browser); a request without one gets 401 `{ signIn: 'required' }`. Pairing is a POST from the Lookout's own page only: a link carries its code in the fragment (`#pair=`), which no server sees, and the page pairs on a click. `/sign-in/…` (`signInRoutes.ts`) lists, pairs and revokes browsers, and issues stream tickets. A `device` session marks its request as another device's (`deviceRequests.ts`), so `fromThisMachine` is false for it even over loopback. Every request to the bridge and the projects hub first passes `requestGuard.ts`: `Host` must be `localhost` or an IP address and an `Origin` must be the server's own, which is what stops DNS rebinding and cross-site requests. The raw file route only touches tracker markdown, never a dot folder or a config file. Routes that change what runs on this machine or whom it trusts (tokens, tracker connection, Slack, risk policy, workspaces, guides, the projects list) answer this machine only, by socket address (`fromThisMachine`); `thisMachineRoutes.ts` is the one list of them (reads that use stored tracker credentials included), and `GET /machine` tells the page which side it is on. Another device on the network can still read, answer and approve; what it reads goes through `redactForLan.ts` (no absolute paths, no tracker account). Tests and end-to-end scripts set `$TEAMTRAIL_NO_GH_CLI` and clear the shell's tokens, so they never use the credentials of whoever runs them. Its route handlers are in `*Routes.ts` (the GitHub repo picker's `GET /trackers/github/repos` is `githubRepoRoutes.ts`, mounted by `trackerRoutes.ts`, with the login and repo lookups cached per token in `githubLookups.ts`; Sign in with GitHub (OAuth device flow) is `POST /trackers/github/sign-in/start|poll|cancel` and `DELETE /trackers/github/sign-in` (sign out) in `githubSignInRoutes.ts`, its state in `githubSignIn.ts`, GitHub's endpoints in `adapters/remote/github/requestDeviceCode.ts` and `pollDeviceToken.ts`, and the OAuth app's client id in `adapters/remote/github/githubClientId.ts` (`$TEAMTRAIL_GITHUB_CLIENT_ID` overrides it, `$TEAMTRAIL_GITHUB_WEB` points it at a fake); the Linear pickers' `GET|POST /trackers/linear/teams` and `/trackers/linear/projects` are `linearTeamRoutes.ts`, with the viewer, team and project lookups cached per key in `linearLookups.ts`), `GET /models` (`modelRoutes.ts`), `/remote-agents` (`remoteAgentRoutes.ts`: the tokens and endpoints, `POST /remote-agents/tokens` and `/remote-agents/tokens/revoke`, journaled, refused cross-site; `watchRemoteAgents.ts` sends the `remote-agents` event), the projects hub in front of it (`projectsHub.ts`: `/projects` routes in `projectRoutes.ts`, `/p/<id>/…` forwarded to that project's bridge, the `projects` event from `watchProjects.ts`), every server's top-level guard (`neverCrash.ts`, `requestUrl` in `http.ts`) and security headers (`securityHeaders.ts`), what another device on the network may not change (`thisMachineRoutes.ts` for routes, `trustFields.ts` with `lanFileRefusal.ts` and `lanCallRefusal.ts` for trust fields whatever the route) and may not read (`redactForLan.ts`, `redactResponse.ts`, JSON and SSE), checks on main (`mainChecksRoutes.ts`: `GET /main-checks?mapId=`, `POST /main-checks/run` and `/main-checks/choose`; `watchMainChecks.ts` starts the runs trails ready for work need and sends the `main-checks` event), the `/events` SSE stream and the background loops (`watchLeases.ts`, `watchVerification.ts`, `watchTrackerFolder.ts` (it hears the folder through `packages/core/src/lib/watchTree.ts`: one watch per folder on Linux, where Node's recursive watch goes deaf to a file replaced by rename, as every tracker write replaces it), `watchAttention.ts`, `watchIntegration.ts`, and `watchMachineStore.ts`: this project's records in the machine store live outside the watched folder and are written by every process (any tab or device, `teamtrail approve`, MCP servers), so it polls them by stamp and sends a `trust` event naming the files that changed (`approvals.json`, `signed-state/<trail>.json`, …), and `sign-in` when browsers are paired or revoked). Evidence never arrives as a path: `verificationEvents.ts` turns it into `verification` events (`kind: 'evidence'`, the trail's file-safe id).

### MCP server (`packages/cli/src/mcp`)

- `server.ts` creates the server; `toolKit.ts` defines how tools are declared (zod schemas, results and errors).
- Tools are grouped in `tools/` (`trailTools.ts`, `ticketTools.ts`, `workTools.ts`, `hitlTools.ts`, `knowledgeTools.ts`, `rerouteTools.ts`, `projectTools.ts` with the read-only `projects_status`, `guideTools.ts`, `proofTools.ts` with the read-only `proof_report`, `memoryTools.ts` with the read-only `find_precedent`). Their behaviour lives in `trail/` (trail ops, ticket ops, HITL, completion, reviews, leases, sessions, the risk check, the attention summary, assumptions and reroutes, parallel work in `parallel.ts`, model matching in `models.ts`, and guides in `guides.ts`: a claim's and a listing's `guides`, each with instructions, checklist and required checks, `guideChecklists.ts` for the checklists a completion answers, and `guideChanges.ts`, which tells the working agent at its next `report_progress` (`guidesChanged`) of a guide the trail lead added or removed mid-work; a completion refused for a guide added since the claim hands that guide over too).
- Every tool that suggests work (`next_ticket` and its wait, `claim_ticket` without a ticket, `resume_trail`, `start_trail` and `close_ticket`'s `next`) asks one chooser, `trail/offerNext.ts`: it reads every claim gate once (discovery, the review limit, checks on main, reroute freezes, criteria before work, own and deferred reviews, model matching, the agent's guides, an archived trail), so an offer is always a ticket `claim_ticket` takes, and when there is none every result gives the same reason (`trail/whyNothing.ts`; `nextReason` beside a null `next`). `claim_ticket` checks a named ticket against the same gates. `packages/cli/test/mcp-offer-agree.test.ts` holds them to one gate per row. The agent's ticket cache (`trail/agentContext.ts`) is keyed by trail and ticket, since a ticket id can repeat across trails.
- `next_ticket` with `wait` (`trail/waitForWork.ts`) waits, holding nothing, until something on the trail becomes claimable for the agent or `waitSeconds` pass (default 120, max 600, 50 for Codex), then returns what `next_ticket` returns plus `waited` (what woke it, `timeout`, or `nothing-open` when the trail has no open ticket). It wakes on changes, not a tight poll: `trail/workSignal.ts` hears the tracker folder and this machine's approvals through core's `packages/core/src/agents/watchWorkChanges.ts` (one shared watch per folder; `workChangeLabel.ts` says which files can free work: tickets, criteria, briefs, reroutes, project settings, checks on main, never session docs, logs or temp files) and the agent's own tracker, and checks again every 15 s besides (5 s for a GitHub or Linear tracker). Progress every 15 s keeps clients waiting, and a call in progress keeps an HTTP session from being closed as idle (`http/createMcpHttp.ts`).
- `http/` is MCP over streamable HTTP, built on the SDK's transport and separable from the rest: `createMcpHttp.ts` is a request handler that takes `auth` and `open` and knows nothing about where it's mounted (a hosted workspace mounts the same handler with its own). It checks host and origin (`requestRefusal` in `packages/core/src/server/requestGuard.ts`, shared with the bridge), then the bearer token (`bearerToken.ts`), then the session, which only the token that opened it may use; sessions end on the client's DELETE, a revoked token, an hour without a call (an open notification stream is not a call), or when their token opens more than 8 (`sessionLimits.ts`). Locally, `tokenFileAuth.ts` reads the repo's token file and `remoteAgentOpener.ts` gives every HTTP session its own `TrailAgent`, marked `remote`. `runMcpHttp.ts` is `teamtrail mcp --http` (only `/mcp` on its port); `packages/cli/src/serve/lookoutHandler.ts` mounts the same handler at `/mcp` on the Lookout's port, and the dev server does in `apps/lookout/plugins/trackerFs.ts`: both with `thisMachineOnly`, because that port also serves the Lookout, whose sign-in is for browsers, not agents. Only `mcp --http` is meant to be shared. A token never opens bridge routes. Tools that would assume the agent's files are on this machine check `ctx.remote` (no worktree, no local checks or git evidence, no `projects_status`). A remote agent never speaks for the human: every tool declares `human` in its definition (`none`, `acts` or the `inputs` that claim the human's word), and `packages/cli/src/mcp/remoteGate.ts` is the one place that applies it (tools that act for the human are not registered for remote sessions and a call is refused with the reason; those inputs are refused). For every agent, local or remote, a HITL ticket closes only after an answer to a question asked on it, given in the Lookout or Slack and not as an fyi (`assertHumanDecided` in `remoteGate.ts`, one rule for both). A new tool that answers, approves or changes a trail lead's setting must declare `acts`; `packages/cli/test/mcp-http.test.ts` pins the list. For every agent, local too, a decision is the human's only by their answer to a question (`trail/humanAnswer.ts`): the answer is tied to the question as asked, its ticket and its risk category, backs one decision, and the record keeps their words; nothing a tool is passed can say who decided. Only an answer given in the Lookout or Slack backs a decision, and only one given in the Lookout (not `lookout-limited`) backs a high-risk call (Slack answers pass through Teamtrail's Scout service; `approvesHighRisk`): every answer carries how it was given (`lookout`, `lookout-limited` for a Lookout caller an embedding server's sign-in denies high-risk calls, `slack` or `chat`; `packages/core/src/model/answerVia.ts`), set by the path that wrote it and signed with it, and a `chat` answer (`answer_question`) is delivered as guidance but refused at every gate, as is an unlabelled one from before labels. The label and the author come from the route that wrote the answer, never from its body; that the human gave a `lookout` answer rests on the Lookout's sign-in: only a signed-in browser reaches its answer route. The trail lead's settings an agent may ask about (`start_trail discovery: false`, `update_trail` mode and destination) never change on its call, local or remote: the call becomes a request in the reroute flow's `setting` lane (`trail/settings.ts`; ops `skip_discovery`, `set_mode`, `update_destination`), which the trail lead approves or declines in the Lookout (the reroute dialog) or Slack (`packages/connector-slack/src/service/settingRequests.ts`, owner-checked); approving is bound to the request's hash, journaled, and kept as their decision (`planning/reroute/recordSettingDecision.ts`). Remote sessions can't make these requests at all. With the markdown tracker, ticket, decision and map files are repo files an agent can also edit directly: the MCP gates bind MCP calls, not file edits; what the gates read counts on this machine only as Teamtrail wrote it here, so a direct edit waits for the human (see Signed state above). Every string a tool takes is a single line unless declared with `text()`, and every input has a maximum size (`lineSafety.ts`, applied by the tool kit from the tool's own schema); `packages/cli/test/mcp-line-safety.test.ts` walks every tool and pins the free-text fields.
- `instructions.ts` holds the server instructions every agent gets. `packages/cli/commands/scout.md` is the `/scout` command for Claude Code (and the Codex prompt).

- A done trail is `features/trail-done/` (wired in `app/useTrailDoneUi.tsx`): judged by core's `trailDone` (`judgeTrail.ts`) once every done ticket's proof, the trail's checks on main together and whether discovery was skipped (`GET /briefs` `skipped`) have loaded, it walks the map's last stretches and plants a flag at the destination (`features/map/MapDestination.tsx`; red when the checks fail on main together), shows in the Current trail step, and opens Destination reached once per trail and outcome in this browser (reached, verified together, a failed run; `useTrailDoneDialog.ts`), leading to the checks failing on main or the done tickets whose pull requests are still open.
- The trail's checks on main together are `features/trail-checks/` (`TrailChecksSection.tsx`): the bubble on the destination (selection `together`), and the trail at a glance once it is done, with Add a fix ticket, Run again, and Run now before everything is merged (`trailChecksActions.ts`).
- Verified by Teamtrail is `features/proof/`: the inspector's Proof section (`TicketProof.tsx`, from `GET /proof/ticket`: the verdict, each gap with who is on it and the human's action where it's theirs (`ProofGapList.tsx`; the first of those is the footer's primary, `features/inspector/gapActionList.ts`), with the digest, the posted comment's link and the key file to commit behind Details; Copy proof for PR is in the ticket's "⋯" menu) and Settings → Project → Proof on pull requests (`ProofPostSection.tsx`).
- A ticket's pull request, as PR sync last read it, is one block under its state line in the bubble and the full ticket (`features/pr-sync/PullRequestBlock.tsx`, its content from `prBlock.ts`): the state as a chip, the checks, whether it is (or was merged) at the commit the proof covers or a newer one, and Open pull request through `webUrl`; its map card shows a PR chip when the row has room (`features/map/prChip.ts`).
- Guides are `features/guides/`: Settings → Project → Guides (`GuidesSection.tsx`), Settings → This trail → Guides by type (`TrailGuidesSection.tsx`, one `TypeGuidesRow.tsx` per ticket type, a toggle per approved guide; `?settings=trail-guides`), and the inspector's How section (its guides by name, `TicketGuideNames.tsx`; Edit opens `TicketGuides.tsx`: a chip per guide marked by type, added or removed, with remove or put back, and Add a guide, for that ticket alone). A map card names only a guide added to its ticket.
- Settings → Remote agents is `features/remote-agents/` (`RemoteAgentsSection.tsx`, data from `useRemoteAgents.ts`): the endpoints, one row per token, and the new token shown once with its connect command.
- Settings is a full page that covers the map, like the Logbook (`features/settings/SettingsPage.tsx`): a side nav of groups (`features/settings/settingsGroups.ts`) and one group at a time, each rendered by its group component (`TrailGroup.tsx`, `ProjectGroup.tsx`, …) from the unchanged section components. `?settings=<group or section>` opens it there (`?settings=guides`, `?settings=slack`); `app/useSettingsPage.ts` keeps the URL in step so the browser's Back returns to the Lookout. On a phone the nav is a list that drills into one group.
- Release notes live in `features/settings/releases.ts` (and the older files beside it): the newest release is the product version and feeds the GitHub release; the Lookout no longer shows them.

## Conventions

Follow `CONTRIBUTING.md`: one export per file, 200 lines max, the layout rules, inline type imports, naming, where tests and fixtures go, its **Readable code** rules (no nested ternaries, early returns, flat nesting, object parameters, small functions, explicit variants), and its **Presenting data** rules for the UI (three levels, four type roles, red only for "needs you now", say it once, lists built from `Row` and `MetaLine`). Lint enforces the mechanical ones; write the rest in the same spirit. Run `npm run format` on files you touch.

## Recipes

**Add an MCP tool.**
1. Declare it in the right `packages/cli/src/mcp/tools/*Tools.ts` with a zod schema, title and description; mark read-only tools `readOnly`. State `human`: `'none'`, or `acts` / `inputs` when it speaks for the human, which keeps it from remote agents. String inputs are single-line by default; declare free text with `text()` and make sure the serialiser that stores it guards it (`model/safeText.ts`).
2. Put the behaviour in `packages/cli/src/mcp/trail/`, with core logic in `packages/core` when it's more than glue.
3. Describe when to use it in `packages/cli/src/mcp/instructions.ts` and `packages/cli/commands/scout.md`.
4. Cover it in `packages/cli/test/` (`mcp*.test.ts`) and drive it end to end in `scripts/verify-mcp.mjs`.

**Add a bridge route and SSE event.**
1. Add a `handleX(req, res, ctx)` in `packages/core/src/server/<name>Routes.ts` that takes the shared `RouteContext` (`routeContext.ts`) and returns `true` when it handled the request, following `leaseRoutes.ts`.
2. Mount it in `trackerBridge.ts` next to the others.
3. Push changes with `send('event: x\ndata: …\n\n')` from a route or a loop (see `watchLeases.ts`), and subscribe in `apps/lookout/src/hooks/useLookout.ts`.
4. Trail lead-only actions are journaled. A route that changes what runs on the machine or whom it trusts goes in `packages/core/src/server/thisMachineRoutes.ts`.
5. A new route is signed in by default: the projects hub's `signInGate.ts` answers before any route, so it needs nothing for that. Never mount a bridge's `handle` without the hub in front, and add nothing to `signInPublicRoutes.ts`.

**Add a journal entry kind.** Extend the entry types in `packages/core/src/model/lifecycle.ts` and keep the reader in `journalFile.ts` tolerant of unknown kinds. Old journals must still load. Add a test with a mixed old and new journal.

**Add a lookout zone, view or setting.**
1. Create `apps/lookout/src/features/<name>/` with an `index.ts` barrel, and styles in `styles/`.
2. Settings sections go in `features/settings/` (see `SettingsSection.tsx`): add the section to its group in `settingsGroups.ts`, render it in that group's component inside a `SettingsSlot` (which notes whether it's committed to the repo or only on this machine), and it gets its own `?settings=<section>` link. Full views opened from the header follow `features/decisions/`.
3. Check the wide, laptop and phone layouts (`App.tsx`, `app/PhoneView.tsx`); a new page over the map goes in `app/RecordViews.tsx` and `app/tabs.ts`. Zone titles carry an info tip (`components/ui/InfoTip.tsx`).

**Version and release notes.** Every feature PR raises the product version: bump the minor in `packages/cli/package.json` and add a release at the top of `RELEASES` in `apps/lookout/src/features/settings/releases.ts` with that version, the date and 1–4 short, user-facing lines (what changed for the user, not how). A fix PR bumps the patch; add a line only if users would notice. `NEXT` only teases what's coming. `apps/lookout/test/productVersion.test.ts` fails if the two versions differ, and `next` builds publish as `<version>-next.<run>`.

**Extend the end-to-end check.** `scripts/verify-mcp.mjs` drives a real trail through the built CLI and a browser. Add steps for new tools or UI, assert on what the user sees, and avoid timing races: wait on state, not sleeps. A step that starts its own Lookout signs its browser in with the link the CLI prints (`lookoutLinks` and `signInWith` in `scripts/e2eHelpers.mjs`), a second browser with a link from `teamtrail pair` (`pairLink`), and calls the API through `page.request` with that page's session (`sessionHeaders`).

## Checks

- `npm run check` runs everything CI runs: lint, the Prettier check, typecheck, build, the vitest and node:test suites, and `verify:mcp` (needs a build and Chrome; set `CHROME` to its path). It must pass before a PR.
- **Run the app on the dev seed:** `npm run dev` resets the dev project to the seed and starts the Lookout with hot reload. The dev server signs in like the CLI: it serves on `http://127.0.0.1:7477` only (not 5173, which agents' own dev servers take; `strictPort`, with `[::1]:7477` held by `apps/lookout/plugins/holdIpv6Loopback.ts`), prints a one-time link when it starts and writes the signed Lookout lock; `npm run dev:pair` (the built `teamtrail pair`, `scripts/dev-pair.mjs`) prints another (`apps/lookout/plugins/trackerFs.ts`). No request makes a code. The dev server serves the repo's files without the built Lookout's script CSP: don't browse untrusted repos with it. `npm run build -w teamtrail && npm run dev:agent` adds real MCP agents working it. `npm run dev:empty` starts on a brand-new empty tracker folder instead, for the first-run flow. `npm run dev:fresh` is a first-time user from nothing: a new git repo, an empty user config dir and a new browser profile, served by the built CLI (`scripts/dev-fresh.mjs`).
- `main` is protected: one PR per change, merged after CI passes. Releases are covered in `CONTRIBUTING.md`.
